# Running the collector in containers

The collector ships as two containers, run with docker compose:

| Container | What it is |
|---|---|
| `collector` | `collector_daemon.py` with the scripts and plugins: the image `fortifydata/collector-ad`, built from `Dockerfile` |
| `postgres` | PostgreSQL 17 (the official image), the collector's database |

The daemon itself (schedule, steps, retries, health, logs) is described in
`DAEMON.md`. This document covers the image, the installation and
day-to-day operation.

| File | What it is |
|---|---|
| `Dockerfile`, `.dockerignore` | Builds the collector image |
| `docker/compose.yaml` | The two services, their networks, volumes and secrets |
| `docker/collector.toml` | The daemon configuration for the container (paths inside it) |
| `docker/install.sh` | Creates or updates an installation directory |

## 1. Design

- **The database stays inside.** PostgreSQL is on an internal network with
  no route out and no published port; only the collector reaches it. Its
  password is generated by `install.sh` and never leaves the machine. Its
  data is in the Docker volume `fortifydata-collector_pgdata`.
- **The collector reaches out only.** It connects to the domain
  controllers (LDAP/LDAPS, SMB for SYSVOL, DNS), and, when configured, to
  Microsoft Graph and the FortifyData API. Nothing connects to it.
- **Least privilege.** The collector runs as a non-root user (the owner of
  the installation's files), with a read-only root filesystem, all Linux
  capabilities dropped and `no-new-privileges`. It writes only to
  `data/state`, `data/logs` and a `/tmp` in memory.
- **Secrets are files.** They are mounted at `/run/secrets/<name>` from
  `secrets/` (mode `0600`). They are never in the image, in an environment
  variable or in `compose.yaml`. The daemon hands them to each step through
  a pipe (see `DAEMON.md`, section 4).
- **Stopping.** `docker compose stop` sends SIGTERM through Docker's init
  process (`init: true`). The daemon then:
  1. stops the running step and waits for it (up to 240 s);
  2. releases the license lease;
  3. exits 0.

  The stop grace period is 5 minutes, so Docker never kills it first.
- **Health.** The container healthcheck runs
  `collector_daemon.py --healthcheck`, so `docker compose ps` shows
  `healthy` while the daemon is alive and reporting. A wrong AD password
  does not make the container unhealthy, because a restart would not fix
  it. The daemon's state and the last run's errors are in
  `data/state/status.json` and the logs.
- **Logs.** `docker compose logs collector` shows everything the daemon and
  the scripts print. Docker keeps 5 files of 10 MB each. The daemon also
  writes `data/logs/collector_daemon.log` (rotated daily) and each script's
  log file in `data/logs/scripts`, both kept 30 days.

## 2. The image

The image is published on Docker Hub as `fortifydata/collector-ad`, for
`linux/amd64` and `linux/arm64` (one multi-platform tag; Docker pulls the
host's architecture). Its tags:

| Tag | What it is |
|---|---|
| `vX.Y.Z` | a release, e.g. `v1.2.0`. Install and pin these. |
| `latest` | the newest release |
| `vX.Y.Z-dev.N` | a development build of the version being prepared, N the CI run number |
| `develop` | the newest development build |

The version the image reports to the platform (and in
`collector_daemon.py --version`) is its tag without the `v`: `1.2.0`, or
`1.2.0-dev.17`. It comes from the `COLLECTOR_VERSION` build argument. Releases
are built and pushed by CI (`.github/workflows/collector-image.yml`, see
`MAINTAINERS.md`), never by hand.

To build one locally, from the repository root:

```
docker build --build-arg COLLECTOR_VERSION=1.2.0 -t fortifydata/collector-ad:v1.2.0 .
docker save fortifydata/collector-ad:v1.2.0 | gzip > collector-ad-1.2.0.tar.gz
```

- **Size:** the image is about 400 MB, about 85 MB compressed. It includes
  the PostgreSQL 17 client tools (`pg_dump`, `pg_restore`, `psql`), for the
  backup taken before a schema migration (section 5).
- **Base images:** the official `python:3.13-slim-trixie` and
  `postgres:17-trixie`. When Docker Hub rate-limits anonymous pulls, use a
  mirror of the same official image:
  - for the build: `--build-arg PYTHON_IMAGE=mirror.gcr.io/library/python:3.13-slim-trixie`;
  - for the database: set `POSTGRES_IMAGE=mirror.gcr.io/library/postgres:17-trixie`
    in `.env`.
- **Dependencies:** they are installed from wheels only
  (`--only-binary=:all:`), so the image needs no compiler.

## 3. Installing

On a Linux host with Docker Engine and the compose plugin:

1. **Create the installation directory.** As the user who will own the
   installation (or as root, in which case the collector runs as uid 10001):

   ```
   docker/install.sh /opt/fortifydata-collector
   ```

   It creates:

   ```
   /opt/fortifydata-collector/
       compose.yaml
       .env                       image names, the collector's uid/gid, optional proxy
       config/collector.toml      the daemon configuration -- edit it
       secrets/pg_password        generated
       secrets/ad_bind_password   empty -- fill in
       secrets/entra_app_secret   empty -- fill in if [entra] is used
       secrets/fd_activation_key  empty -- fill in to push results
       data/state/                instance id, status.json, state.json, reports,
                                  backups/ (database backups taken before a migration)
       data/logs/                 collector_daemon.log, scripts/
   ```

2. **Get the image.** In the installation directory, `docker compose pull`
   fetches it from Docker Hub. On a host without access to Docker Hub, load
   it from a file instead:

   ```
   docker load -i collector-ad-1.2.0.tar.gz
   ```

3. **Prepare the accounts.** The client's administrators set up the AD
   service account and, if Entra ID is assessed, the App Registration.
   Hand them `PERMISSIONS.md`, which also lists the network access the
   collector needs.

4. **Configure** `config/collector.toml`:
   - the schedule;
   - `[ad]`: DC, account, domain;
   - optionally `[entra]`;
   - to push, uncomment `activation_key_file`.

   For LDAPS verification, put the CA certificate in `config/` and set
   `ca_cert_file = "/config/<file>.pem"`.

5. **Write the secrets**, one per file, on the first line:

   ```
   printf '%s\n' 'the bind password' > secrets/ad_bind_password
   ```

6. **Check, then start:**

   ```
   cd /opt/fortifydata-collector
   docker compose run --rm collector --check-config
   docker compose up -d
   docker compose logs -f collector
   ```

   On its first start the daemon creates the schema and runs at once. It
   then runs daily at the configured time.

`--check-config` can be run at any time, also while the daemon runs. To
run once by hand, stop the daemon first, because only one process may use
the state directory at a time:

```
docker compose stop collector
docker compose run --rm collector --once
docker compose start collector
```

**Proxy.** Set `HTTPS_PROXY` (and `NO_PROXY`) in `.env` for the outbound
calls to Microsoft Graph and the FortifyData API. Behind a TLS-inspecting
proxy, also put its CA certificate in `config/` and set
`[platform] ca_bundle`.

**DNS.** The container resolves names through the host. If the host
cannot resolve the AD domain, set `dns:` in `compose.yaml`.

**FortifyData mode.** Set `mode = "fortifydata"` and `activation_key_file`,
and put the activation key in `secrets/fd_activation_key`. The configuration
then comes from the portal, with the health check:
- the `[schedule]`, `[ad]` and `[entra]` sections are ignored;
- the AD and Entra secret files can stay empty.

## 4. Operating

| Task | Command (in the installation directory) |
|---|---|
| Status | `docker compose ps`; `cat data/state/status.json` |
| Logs | `docker compose logs -f collector`; `data/logs/` |
| Stop / start | `docker compose stop` / `docker compose start` |
| Change the configuration | Edit `config/collector.toml` (local mode: picked up before the next run; a failed run is retried at once). Daemon settings ([daemon], [platform], [database]) need `docker compose restart collector`. |
| Change a secret | Rewrite the file in `secrets/`. AD and Entra secrets are re-read before every run. A new activation key needs `docker compose restart collector`. |
| Back up the database | `docker compose exec -T postgres sh -c 'PGPASSWORD="$(head -n1 /run/secrets/pg_password)" pg_dump -h 127.0.0.1 -U adprofiler -Fc adprofiler' > adprofiler-$(date +%F).dump` |
| Back up the rest | `config/`, `secrets/` and `data/state/` (which holds the pre-migration backups in `backups/`) |

**The database password** is set when the database is first created.
Changing `secrets/pg_password` afterwards does not change it. To change it,
run `ALTER ROLE adprofiler PASSWORD '…'` in the database first, then
rewrite the file and restart both containers.

**Removing everything** needs `docker compose down -v`. The `-v` deletes
the database volume, so leave it out to keep the data.

## 5. Upgrading

In FortifyData deployments the Collector Manager does this. By hand:

1. Run the new `docker/install.sh` on the installation directory. It
   replaces `compose.yaml`, keeping the old one as `compose.yaml.previous`,
   and changes nothing else.
2. Set `COLLECTOR_IMAGE` in `.env` to the new tag, e.g.
   `fortifydata/collector-ad:v1.3.0`.
3. Run `docker compose pull collector` (or `docker load` the file), then
   `docker compose up -d`.

The daemon brings the database up to the new image's schema at the start of
its next run: `schema_setup.py` applies every migration in the image's
`migrations/` folder above the database's version, in order. Skipped updates
need no special handling, because the newer image carries all the migrations
in between. When a migration needs a full rescan, the next collection does
it.

**The backup before a migration.** Before it applies any migration to an
existing database, `schema_setup.py` dumps the database with `pg_dump` to
`data/state/backups/adprofiler-v<from>-before-v<to>-<UTC time>.dump`
(custom format, mode `0600`). If the backup fails, no migration is applied
and the run fails, so the database is never migrated without one. The
newest 3 backups are kept. A run with no migration to apply takes none.

**Going back to the previous version.** A newer schema is not guaranteed to
work with an older image, so restore the backup along with the image:

```
docker compose stop collector
ls data/state/backups/                          # pick the newest .dump
docker compose run --rm --no-deps -T --entrypoint sh collector -c '
  export PGPASSWORD="$(head -n1 /run/secrets/pg_password)"
  export PGOPTIONS="-c client_min_messages=warning"
  psql -h postgres -U adprofiler -d adprofiler -v ON_ERROR_STOP=1 \
       -c "DROP SCHEMA ad_intel CASCADE"
  pg_restore -h postgres -U adprofiler -d adprofiler --no-owner --exit-on-error \
       /var/lib/fortifydata-collector/backups/<file>.dump'
```

Then set `COLLECTOR_IMAGE` in `.env` back to the previous tag and run
`docker compose up -d`. The data collected since the backup is lost; the
next run collects afresh. A database older than v50 (test installations from before the baseline)
cannot be upgraded: `docker compose down -v` deletes the database volume,
then `docker compose up -d` creates it afresh.

PostgreSQL minor versions come with a newer `postgres:17-trixie` image
(`docker compose pull postgres`). A major-version upgrade (18) needs a dump
and restore and is not automated.

## 6. Testing done

These were tested with Docker Engine 29 and compose v5, on cgroup v1:

- **Build:** the image builds for `linux/amd64` and `linux/arm64` (the
  latter under QEMU emulation), and the daemon reports its versions inside
  it, with the version given at build time.
- **Backup before a migration:** a failing `pg_dump` stops the migration
  (the database stays at its version); a working one writes the backup and
  then migrates; restoring it as above brings back the previous version and
  its data; only the newest backups are kept.
- **Install script:** fresh, run again (nothing overwritten), as root (uid
  10001) and as an ordinary user (that user's uid).
- **Configuration check:**
  - an empty AD password file is reported (exit 78);
  - a correct one passes;
  - it works while the daemon runs;
  - `--once` while the daemon runs is refused (exit 75).
- **Local mode:** on first start the schema was created in the PostgreSQL
  container. adprofiler failed cleanly on an unreachable DC, and the
  container stayed healthy.
- **FortifyData mode, with a mock platform:**
  - lease, encrypted configuration and health reports;
  - adaudit evaluated and pushed the run with the license key;
  - adprofiler was replaced by a stand-in (no DC in the test).
- **Stopping and restarting:**
  - `docker compose stop` while idle, and while a step was running: the
    step got SIGTERM and exited 130, the lease was released, and the
    container exited 0 within 2 s;
  - a restart did not repeat the day's run;
  - a platform that cannot be reached is reported and retried.
- **Backup:** the `pg_dump` command above.
